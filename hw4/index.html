Overview

In this assignment, we implemented a real-time cloth simulation using a mass-and-spring system. We started by building the data structures to discretize the cloth into point masses connected by structural, shearing, and bending springs (Part 1). We then applied Verlet integration to simulate how the cloth moves over time under external forces like gravity and internal spring forces (Part 2). Next, we handled collisions with other objects such as spheres and planes (Part 3), and then self-collisions using spatial hashing to prevent the cloth from clipping through itself (Part 4). Finally, we wrote several GLSL shader programs to render the cloth with realistic lighting and material effects on the GPU (Part 5).

Part 1: Masses and springs

Quick explanations on implementation: In Cloth::buildGrid, we first populate the point_masses vector in row-major order, setting the positions based on the cloth's orientation (horizontal or vertical). We then mark any pinned masses according to the cloth's pinned vector. After all point masses are placed, we create three types of springs: structural (connecting each mass to its left and upper neighbors), shearing (connecting each mass to its diagonal upper-left and upper-right neighbors), and bending (connecting each mass to the mass two positions to its left and two positions above). That's it.

Part 2: Simulation via numerical integration

With the cloth structure in place, we implemented Verlet integration to simulate the cloth's motion over time. At each timestep, we compute external forces (gravity) and internal spring forces, then update each point mass's position using Verlet integration with damping. We also enforce a constraint that springs should not stretch beyond 10% of their rest length as mentioned in the hw spec.

We experimented with several parameters using scene/pinned2.json:

Spring constant (ks)

With a very low ks (e.g. 5 N/m), the cloth is very loose and stretchy. It sags deeply in the middle and the top edge droops significantly between the two pinned points, producing many visible ripples. With a very high ks (e.g. 50000 N/m), the cloth is very stiff. It barely sags, the top edge stays nearly straight, and the cloth quickly reaches a flat, taut rest state with little deformation.

Density

Increasing density (e.g. 150 g/cm²) makes the cloth heavier, so gravity pulls it down more. The effect is similar to lowering ks, with a deeper sag and more folds. Decreasing density (e.g. 1.5 g/cm²) makes the cloth lighter, so it hangs more tautly with very little droop, similar to raising ks.

Damping

With very low damping (e.g. 0%), the cloth swings back and forth for a long time before settling, oscillating like a pendulum. With high damping (e.g. 1%), the cloth falls very slowly and smoothly to its rest state with no oscillation at all, as if it were moving through a viscous fluid.

Part 3: Handling collisions with other objects

We implemented collision handling for two primitive types: spheres and planes. In both cases, the goal is the same: if a point mass has penetrated (or is about to penetrate) the primitive, push it back onto the correct side of the surface and scale the correction from last_position by (1 - friction) so that some tangential velocity is lost, mimicking a simple friction model.

Sphere collisions: We first compute the vector to_pm = pm.position - origin from the sphere center to the point mass and its length dist. If dist >= radius, the point is outside the sphere and we simply return with no correction. Otherwise, the point has fallen inside the sphere and we need to project it back out. We compute the tangent point on the sphere surface by walking from the origin along the unit direction to_pm.unit() for a distance of radius, i.e. tangent_point = origin + to_pm.unit() * radius. The correction vector correction = tangent_point - pm.last_position is the displacement needed to move the point from its previous (valid) position to the tangent point. We then set pm.position = pm.last_position + correction * (1 - friction), which lands the point just on the sphere surface and implicitly damps tangential motion.

Plane collisions: The plane is defined by a point point and a normal normal. We compute the signed distances of last_position and position relative to the plane as d_last = dot(last_position - point, normal) and d_curr = dot(position - point, normal). As a safety net, if d_curr < 0 (the point has somehow ended up on the wrong side of the plane), we snap it back to last_position + normal * SURFACE_OFFSET. For the normal crossing case we check d_last * d_curr < 0, which means the segment from last_position to position crossed the plane. We then parametrize the segment as last_position + t * (position - last_position) and solve for the intersection parameter t = d_last / dot(direction, normal), giving the tangent point on the plane. We nudge this tangent point slightly off the plane along the normal by SURFACE_OFFSET to avoid z-fighting and re-penetration, form the correction (tangent_point + normal * SURFACE_OFFSET) - last_position, and apply pm.position = pm.last_position + correction * (1 - friction).

Part 4: Handling self-collisions

We implemented self-collision detection using spatial hashing so we can avoid the O(n²) cost of checking every pair of point masses. The implementation has three pieces:

(1) Hashing a position to a 1D key. In hash_position, we pick bucket dimensions w = 3 * width / num_width_points, h = 3 * height / num_height_points, and t = max(w, h), so each spatial bucket is roughly three primitive spacings wide. We snap the position to the grid by floor(pos.x / w), floor(pos.y / h), floor(pos.z / t), then combine the three integer indices into a single float key using a standard prime-multiplication hash (e.g. a * p1 ^ b * p2 ^ c * p3). This guarantees that two point masses which fall into the same 3D cell always produce the same key.

(2) Building the spatial map. In build_spatial_map, we first free any previously allocated vectors in map and clear it. Then, for each point mass, we compute its hash key. If the key is not yet in map, we insert a new vector<PointMass *>; in either case we push the point mass pointer into the corresponding bucket. After this pass, map lets us look up, for any bucket key, all point masses that currently hash to it.

(3) Applying self-collision corrections. In self_collide, for a given point mass pm we fetch the candidate bucket via its hash key and iterate over every other point mass in that bucket. For each candidate, we compute the separation vector and its length. If they are closer than 2 * thickness, we build a correction along the separation direction that pushes pm outward until the gap reaches exactly 2 * thickness. We accumulate these corrections and track a counter. Finally, we apply the average correction scaled by 1 / simulation_steps to pm.position; dividing by simulation_steps prevents the cloth from jittering when many corrections stack up within one frame.

Because the cells are chosen to be a few times larger than the primitive spacing, most true collisions land in the same bucket, while most far-away pairs hash to different buckets, giving us roughly O(n) behavior in practice.

Part 5: Shaders

What is a shader program?

A shader program is an isolated program that runs in parallel on the GPU, processing parts of the graphics pipeline. A vertex shader runs once per vertex, transforming model-space positions and normals into world-space and screen-space coordinates, and passing per-vertex data (position, normal, UV) as varyings. These varyings are then interpolated across each triangle via barycentric coordinates. The fragment shader runs once per fragment (pixel), receiving the interpolated varyings and computing a final RGBA color for that pixel. So basically, the vertex shader processes vertices and outputs values for rasterization, while the fragment shader shades each generated fragment using the interpolated per-vertex data.

Blinn-Phong shading model

Blinn-Phong combines three lighting components. (1) Ambient: a constant base illumination \( k_a \cdot I_a \) that prevents surfaces from being completely black. (2) Diffuse: \( k_d \cdot (I/r^2) \cdot \max(0, \mathbf{n} \cdot \mathbf{l}) \), which simulates light scattering equally in all directions from a surface, brightest when facing the light. (3) Specular: \( k_s \cdot (I/r^2) \cdot \max(0, \mathbf{n} \cdot \mathbf{h})^p \), which simulates shiny highlights using the half-vector \( \mathbf{h} = \text{normalize}(\mathbf{v} + \mathbf{l}) \) between the view and light directions; the exponent \( p \) controls highlight sharpness.

The four screenshots below isolate each term and then combine them, so we can see exactly what each component contributes:

  • (a) Ambient only: the sphere is lit with a flat, uniform color regardless of surface orientation. There is no sense of shape because the ambient term does not depend on the normal or the light direction; it is purely a constant floor on brightness.
  • (b) Diffuse only: the sphere now shows clear shading that depends on the angle between the surface normal and the light direction. The side facing the light is bright while the opposite side falls off to black, giving the sphere a matte, chalky appearance with no highlights.
  • (c) Specular only: almost the entire sphere is dark except for a small, bright highlight where the half-vector \( \mathbf{h} \) aligns with the normal. This isolates the "shiny" term and shows how the exponent \( p \) concentrates energy into a tight highlight.
  • (d) Full Blinn-Phong: all three terms are summed. The sphere has a non-black shadow side (ambient), smooth directional shading (diffuse), and a crisp highlight where the view and light vectors align (specular), producing a realistic plastic-like look.

Bump mapping vs. displacement mapping

Bump mapping only modifies the surface normal in the fragment shader by sampling a height map and computing finite-difference derivatives (dU, dV). The geometry itself stays flat, so it is purely a shading trick. Displacement mapping actually moves the vertex positions in the vertex shader along the normal by the height map value, creating real geometric detail. At low mesh resolution (-o 16 -a 16), displacement mapping appears coarse and blocky since there aren't enough vertices to capture fine detail, while bump mapping still looks smooth. At high resolution (-o 128 -a 128), displacement mapping produces convincing geometric silhouettes and self-shadowing that bump mapping cannot achieve.

For all the renders below, we used textures/texture_3.png as the height map. Following the hw spec's suggested parameters, we set (normal_scaling, height_scaling) = (2, 1) for bump mapping and (normal_scaling, height_scaling) = (100, 0.02) for displacement mapping.

Mirror shader

The mirror shader computes the outgoing eye-ray \( \mathbf{w}_o = \mathbf{p}_\text{cam} - \mathbf{p}_\text{frag} \), reflects it across the surface normal to get the incoming direction \( \mathbf{w}_i \), and samples the environment cubemap in that direction. This approximates perfect specular reflection without tracing any rays.
